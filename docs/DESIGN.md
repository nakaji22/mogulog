# MoguLog（もぐログ）設計書 — Phase 1

## アプリ名

**もぐログ (MoguLog)** — 「もぐもぐ食べる記録」。Calsee等の既存アプリの名称・ロゴ・画面構成は模倣せず、名称・デザイン・コードはすべてオリジナル。

- Bundle Identifier（仮）: `com.mogulog.app`（公開前に取得済みドメイン等に合わせて変更可。手順は docs/APP_STORE.md）
- 料金モデル: 完全無料。サブスクリプション・アプリ内課金・広告・回数制限・有料限定機能は一切なし。課金SDK自体を組み込まない。

## 技術選定

| 領域 | 選定 | 理由 |
|---|---|---|
| フレームワーク | React Native + TypeScript / Expo SDK 58 | Macなしでも Expo Prebuild で iOSプロジェクトをCI生成できる |
| ルーティング | Expo Router（ファイルベース、タブ5つ） | 標準構成で保守が容易 |
| DB | expo-sqlite（端末内） | オフライン永続化、アカウント不要 |
| 状態管理 | Zustand | 軽量、ストア1つで全画面共有 |
| グラフ | react-native-svg で自作（円形/棒/折れ線） | 追加の重い依存を避け、互換性を確保 |
| 写真 | expo-image-picker（撮影/ライブラリ）+ expo-camera 権限 | システムカメラUIを使い権限処理を確実に |
| ファイル | expo-file-system（新API: File/Directory/Paths） | 写真の永続保存、CSV/JSON書き出し |
| 共有 | expo-sharing / 触覚: expo-haptics | 標準モジュールのみ |
| CI | GitHub Actions（macosランナー） | Macなしで Archive/IPA/TestFlight まで自動化 |

## AI写真解析方式 — 実現可能性と制約（最重要）

### 結論（正直な現状）

**「写真1枚から料理を正確に特定し、重量まで自動計測する」ことは、無料・オンデバイス・無制限の条件では、現時点の公開技術だけでは実用精度に届きません。** 以下が根拠です。

1. **食事認識モデル**: Food-101等の公開データセットで学習した分類モデルは「料理カテゴリの上位候補提示」までは可能ですが、日本の定食のような複合料理（主食+主菜+汁物+副菜の分解）や、見えない調味料・油量の推定はできません。商用アプリの多くは有料のクラウドAPI（GPT-4o等のVLM）を使っており、これは「外部APIコストゼロ」の条件と両立しません。
2. **重量推定**: 単一の2D画像から重量を正確に測ることは原理的に困難です（奥行き・密度が不明）。業界標準の解法は「標準的な一人前の量を初期値として提示し、ユーザーが調整する」であり、本アプリもこれを採用します（要件3.2の指定通り）。
3. **Expoへのモデル組み込み**: Core ML/TFLiteモデルをReact Nativeに組み込むネイティブモジュールは存在しますが、モデルの学習データのライセンス・再配布可否、モデルサイズ、SDK互換性の検証をMacなし環境で完結させることはリスクが高く、「CIで確実にビルドできる」という最優先条件を損ないます。

### v1の実装（嘘のない設計）

`src/lib/analyzer.ts` に解析プロバイダのインターフェースを定義し、2層構造にします。

- **候補提示プロバイダ（実装済み・初期値）**: 写真を受け取り、(a)利用履歴で頻出の食事、(b)内蔵の料理テンプレート（唐揚げ定食・カレーライス等12種、各テンプレートは食材と標準一人前で構成）、(c)食品データベース検索、を「候補」として提示します。UIには「AI自動判定ではなく候補提示である」こと、数値が推定であることを明示します。候補の並びは履歴に基づきますが、写真の内容を判定したとは表示しません。
- **オンデバイス分類プロバイダ（インターフェースのみ・未実装）**: 将来、ライセンスが明確な食事分類モデル（Core ML形式）を `assets/models/` に配置すれば差し替え可能な設計にしています。モデルが無い現状では自動的に候補提示へフォールバックします。**未実装のAIを実装済みと表示することはしません**（アプリ内の表記もこの通り）。

### 栄養データ

- 内蔵食品DB（`src/lib/foods.ts`）: 日本食品標準成分表（文部科学省）の代表値を基にした主要食品 約120品目（100gあたりエネルギー・PFC・食物繊維・食塩相当量）。値は公開データの概数であり、アプリ内とプライバシー/データ注記にその旨を明記します。政府標準データは出典明示の上で利用可能なオープンデータです。
- 料理テンプレート（`src/lib/templates.ts`）: 食品DBの組み合わせで構成し、合計は常に再計算されます。

## データモデル（SQLite）

- `user_profile`（単一行）: 年齢・性別・身長・現在体重・目標体重・活動レベル・目的・算出目標（kcal/PFC）・手動上書き値
- `meals`: id, date（YYYY-MM-DD）, meal_type（breakfast/lunch/dinner/snack）, title, photo_uri, note, source（photo/manual/template）, created_at
- `meal_items`: id, meal_id（FK, ON DELETE CASCADE）, food_id（nullable）, name, grams, servings, kcal, protein, fat, carbs, fiber, salt（保存時に確定した実数値。編集時は食品の100g値から再計算）
- `weights`: date（PK）, weight_kg
- マイグレーション: `PRAGMA user_version` 方式

## 目標カロリー計算と安全設計

- 基礎代謝: Mifflin-St Jeor式。活動レベル係数 1.2〜1.9 でTDEE算出。
- 目的別調整: 減量 −15%（ただし上限 −500kcal）、増量 +10%、維持 ±0。
- **安全下限**: 推奨摂取量が 男性1,500kcal / 女性1,200kcal を下回る場合は下限値に切り上げ、画面に「これ以下は自動推奨しません」と明示。急激な減量ペース（週1kg超相当）は警告表示。
- 算出値は推定であることを常時表示し、ユーザーが手動で上書き可能。

## 画面構成

- オンボーディング（初回のみ）→ プロフィール入力と目標算出
- タブ: ホーム / 記録 / **カメラ（中央・強調）** / 分析 / 設定
- モーダル系: 解析候補の選択・編集（analyze）、食品検索・手入力（food-search）、食事詳細・編集（meal/[id]）、体重記録（weight）
